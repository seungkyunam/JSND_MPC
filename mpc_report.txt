## 1. 개발 목표

**왜 Pure Pursuit(PP)를 MPC로 바꾸려 했나** (`controller/docs/MPC_MECHANISM_EXPLAINED.md`)

- **PP의 구조:** 앞쪽 목표점(lookahead) 하나를 보고 기하학적으로 조향각을 정합니다. 속도는 별도의 규칙과 프로파일로 따로 정합니다. 조향과 속도가 서로를 고려하지 않고, 조향각 한계나 조향 속도 한계 같은 물리 제약은 계산이 끝난 뒤에 잘라내는 방식입니다.
- **MPC의 구조:** 약 1초 앞까지 차량 움직임을 예측하고, 가속도와 조향각을 하나의 최적화 문제에서 함께 정합니다. 경로 오차, 속도 오차, 조향 변화, 물리 한계를 한 번에 다룹니다.
- **목표:** 코너 앞에서 미리 감속하고, 제약을 처음부터 지키면서 경로를 더 정확하고 부드럽게 따라가는 제어기를 만드는 것입니다. 실차에서는 계산이 실패하면 무조건 정지하도록 안전하게 운용하는 것도 목표입니다.

> ⚠️ 저장소에는 **같은 맵과 같은 지표로 측정한 PP 비교 기록이 없습니다.** 따라서 "MPC가 PP보다 빠르다"거나 "더 정확하다"는 주장은 아직 근거가 없습니다.

## 2. MPC 설계 (`controller/controller/mpc/integrated_mpc.py`)

| 항목 | 내용 | 쉽게 말하면 |
|---|---|---|
| 차량 모델 | 뒤차축 기준 **Kinematic Bicycle**. 상태 `[x, y, yaw, v]`, 입력 `[가속도 a, 조향각 δ]` | 바퀴 미끄러짐을 무시하고 "앞바퀴 방향으로 굴러간다"고 보는 단순 모델입니다. 저속 F1TENTH에서 흔히 쓰고 계산이 가볍습니다. |
| 최적화 방식 | **LTV-MPC + QP**, solver는 **OSQP** | 비선형 모델을 매 주기마다 현재 기준 궤적 주변에서 직선으로 근사합니다. 그러면 문제가 2차 계획법(QP)이 되어 빠르게 풀립니다. |
| 시간 구조 | 첫 단계는 제어 주기(sim 25 ms), 이후는 0.1 s 간격 | 바로 앞은 촘촘하게, 먼 미래는 듬성듬성 봐서 계산량을 줄입니다. |
| 실행 방식 | 해 전체 중 **첫 입력만 실행**하고 다음 주기에 다시 계산(receding horizon) | 계획을 매번 갱신하므로 오차가 쌓이지 않습니다. |
| 속도 계산 | 웨이포인트 속도 → 곡률로 횡가속도 상한 √(a_lat/κ) 적용 → 뒤에서부터 감속 가능성 계산(braking preview) | 코너가 나오기 전에 감속을 미리 계획합니다. |
| 제약 | 가감속, 조향각, 조향 변화율, 속도 상한, 횡가속도 | 차가 실제로 낼 수 없는 명령은 처음부터 만들지 않습니다. |
| 사후 검사 | QP 해를 비선형 모델로 다시 시뮬레이션해서 횡가속도, 경로 이탈(1 m), heading 오차(0.7 rad), 속도 프로파일 위반을 확인 | 근사로 구한 해가 실제로도 안전한지 한 번 더 확인합니다. |
| 실패 처리 | solver 실패, 시간 초과, 입력 이상, 제약 위반이면 **속도 0의 STOP 요청** | 불확실하면 멈춥니다. 단, STOP 요청이 실제 제동 완료를 뜻하지는 않습니다. |
| 계산 최적화 | OSQP 행렬 구조 재사용, warm start, 선형화 일괄 처리 | 일괄 처리 전후 제어 입력 차이는 최대 8.9e-14로, 결과가 사실상 같습니다(`batched_equivalence.json`). |

**웨이포인트 추종 방식 (`_reference`):**
1. 경로에서 차량과 가장 가까운 지점을 찾습니다.
2. 그 지점부터 예상 속도로 경로를 따라 N개의 미래 기준점(위치, yaw, 속도)을 만듭니다.
3. MPC는 이 기준점과의 차이를 최소화합니다.

시뮬레이션에서는 state machine이 보내는 `/local_waypoints`를 쓰고, 실차에서는 `/global_waypoints`에서 앞쪽 약 200점을 잘라 씁니다.

## 4. 시뮬레이션 결과

**최종 결과:** test0 맵, ROS2 Humble, 노트북(Intel Ultra 7). 근거 파일은 `controller/docs/integrated_validation/ros_test0_tuned40_metrics/result.json`입니다.

| 지표 | 값 |
|---|---|
| 랩 | **3랩 완주**, 충돌 0회, solver 실패·deadline 초과 0회 |
| 랩타임 | 27.41 s (정지 상태에서 출발) / **20.79 s / 20.74 s** |
| 최고 속도 | 1.997 m/s (상한 2.0 m/s에 도달) |
| 횡방향 추종 오차 | RMSE **0.046 m**, 최대 **0.117 m** |
| MPC 계산 시간 | p99 **7.38 ms**, 최대 **14.74 ms** (deadline 20 ms 이내) |
| 제어 주기 | 목표 25 ms(40 Hz)인데 p99 **39.3 ms**, 최대 **89.7 ms** ⚠️ |

**보조 결과**
- 이상적인 kinematic 모델(ROS 없음, `tuned_kinematic/kinematic.json`): 21.5 / 20.82 / 20.82 s, RMSE 0.033 m, 연속 성공.
- 회귀 테스트(`final_regression.xml`, 11/19): 165개 중 실패 0, 건너뜀 1(opt-in DDS 시험).
- 11/17 조향 전용 MPC 오프라인 시험: 64개 통과. 50 Hz 실시간 호출 900회 중 전체 루프가 20 ms를 넘은 경우가 2회 있었습니다.

**해석할 때 주의할 점**
- 이 결과를 얻기까지 문제가 있었습니다. 코너 진입 때 QP가 풀리지 않거나(infeasible) 시간을 초과해서 STOP이 발생했습니다.
  - 원인: 현재 속도가 코너 속도 상한보다 높은데 그 상한을 즉시 강제했고, 조향 제약끼리 충돌했습니다.
  - 수정: 상한을 "감속해서 도달할 수 있는 범위"로 바꿨습니다. 그 뒤 horizon 15→10, max_iter 1000→400, 주기 50→40 Hz로 줄여서 위 결과를 얻었습니다.
- 속도를 2 m/s로 묶은 **보수적인 조건**입니다. 레이싱 성능을 보여주는 결과가 아닙니다.
- 제어 주기 p99가 39 ms로, 목표 25 ms보다 느린 샘플이 많습니다. 아직 CPU 여유가 충분하다고 말할 수 없습니다.
- 노트북에서 측정한 값입니다. **Jetson에서의 계산 시간은 측정하지 않았습니다.**

## 6. 장애물 회피

| 구분 | 상태 |
|---|---|
| MPC 자체의 장애물 제약 | ❌ **없음.** 코드 주석에도 `max_tracking_error`는 "장애물 여유거리가 아님"이라고 적혀 있습니다. |
| 시뮬레이션 회피 경로 추종 | 🔶 state가 GB_TRACK/START/OVERTAKE/RECOVERY일 때는 state machine이 준 local 경로(회피 경로 포함)를 MPC가 따라가도록 **연결만 되어 있습니다.** 장애물이나 상대차를 두고 시험하지는 않았습니다. |
| TRAILING(상대차 추종), FTGONLY | ❌ MPC 모드에서는 **정지**합니다(기존 PP의 상대차 추종 PID와 FTG를 쓰지 않음). |
| 실차 | 🔶 글로벌 경로만 따라갑니다. 회피 기능은 없습니다. gate가 전방 ±35° LiDAR 최소거리 < max(0.35 m, 0.5·v + 0.2 m)이면 **정지**합니다. 피하는 게 아니라 멈추는 방식입니다. |
| 오프라인 합성 회피 경로 | ✅ (11/17, 조향 전용 MPC) RMS 0.017 m, 장애물과 최소 0.98 m. 차체 크기를 무시한 점 차량 시험이라 실제 회피 성능의 근거는 아닙니다. |
| 기존 JSND 회피 플래너 | 보존했습니다(static avoidance, spliner, lane change, SQP, recovery). MPC와 함께 검증하지는 않았습니다. |

## 8. 향후 계획 (제안)

**0단계: 실차 기반 확보 (튜닝보다 먼저)**
1. 오늘 변경을 커밋합니다.
2. Shadow에서 `controller_status`, `raw_command`, 계산 시간을 bag으로 기록해 **Jetson 계산 시간(p99, 최대)**을 측정합니다.
3. 같은 시간대 PP 명령과 MPC 명령을 비교합니다.
4. 조향 부호, ERPM, 휠베이스, E-stop, watchdog을 실측하고 프로파일을 확정합니다.
5. bench(바퀴 띄움, 5초) → 0.2 m/s 저속 drive 순서로 진행합니다.

**1단계: 시뮬레이션 튜닝.** 한 번에 하나만 바꾸고, 같은 맵에서 3랩씩 측정합니다.
1. **계산 예산 (Horizon, dt, max_iter):** 먼저 제어 주기 p99를 25 ms 안으로 들여야 이후 비교가 공정합니다. 예를 들어 N=10/15/20을 Jetson 시간과 함께 봅니다.
2. **추종 정확도 (Q_position, Q_heading):** RMSE와 최대 오차가 줄어드는지 봅니다.
3. **부드러움 (R_steer, Rd):** 조향 변화율과 진동을 봅니다. 지금은 측정 항목이 없어서 지표를 추가해야 합니다.
4. **속도 (max_speed 2.0→2.5→3.0, 횡가속도, braking_preview_ratio):** 랩타임을 줄이되 STOP이 0회인지 확인합니다.
5. terminal_scale은 마지막에 미세 조정합니다.

**공통 비교 지표**
- 랩타임(2·3랩 평균)
- 횡방향 RMSE와 최대 오차
- 최고 속도와 평균 속도
- solver 시간 p99와 최대
- 제어 주기 p99와 최대
- STOP·infeasible·deadline 횟수
- 충돌 여부
- 조향 변화율

**기준선:** 같은 맵에서 **PP로도 같은 지표를 측정**해야 PP 대비 개선을 주장할 수 있습니다.

**2단계: 회피 연동.** 시뮬레이션에서 정적 장애물과 OVERTAKE 경로를 MPC로 따라가는지 검증합니다. 그다음 TRAILING 처리 방법(MPC 속도 상한으로 넣을지 등)을 설계합니다.

## 9. 교수님 보고 대본 (약 5분)

> 교수님, F1TENTH MPC 제어기 진행 상황을 보고드리겠습니다.
>
> **[목표]** 기존 Pure Pursuit는 앞쪽 목표점 하나를 보고 조향을 정하고, 속도는 별도 규칙으로 정합니다. 그래서 조향과 속도가 서로를 고려하지 못하고, 조향 한계 같은 물리 제약은 계산 후에 잘라내는 방식입니다. 저희는 약 1초 앞을 예측하면서 가속도와 조향을 한 번에 최적화하는 MPC로 바꾸는 것을 목표로 했습니다. 코너 전에 미리 감속하고, 제약을 처음부터 지키는 제어기를 만들기 위해서입니다.
>
> **[설계]** 차량 모델은 뒤차축 기준 kinematic bicycle 모델이고, 상태는 위치·방향·속도, 입력은 가속도와 조향각입니다. 매 주기마다 현재 경로 주변에서 모델을 선형화해 QP로 만들고 OSQP로 풉니다. 해 중 첫 번째 입력만 실행하고 다음 주기에 다시 계산합니다. 경로 곡률로 코너 속도 상한을 계산하고, 뒤에서부터 감속 가능성을 따져 미리 감속하도록 했습니다. solver가 실패하거나 시간을 넘기거나 예측 궤적이 제약을 벗어나면 무조건 정지를 요청합니다.
>
> **[구현]** 기존 JSND의 위치추정, 플래너, state machine, 하드웨어 드라이버는 그대로 쓰고 제어기만 교체했습니다. 기존 PP는 지우지 않고 설정 하나로 되돌릴 수 있게 했으며, 회귀 테스트로 PP 동작이 바뀌지 않았음을 확인했습니다. 처음에는 조향만 MPC로 했고, 이후 속도와 조향을 함께 최적화하는 통합 MPC로 확장했습니다. 시뮬레이션과 실차가 같은 MPC 코드를 사용합니다.
>
> **[시뮬레이션 결과]** test0 맵에서 속도 상한 2 m/s의 보수적인 조건으로 3랩을 충돌과 solver 실패 없이 완주했습니다. 랩타임은 출발 랩 27.4초, 이후 20.8초와 20.7초입니다. 횡방향 추종 오차는 RMSE 4.6 cm, 최대 11.7 cm입니다. MPC 계산 시간은 p99 7.4 ms, 최대 14.7 ms로 제한 시간 20 ms 안에 들어왔습니다. 다만 전체 제어 주기는 목표 25 ms인데 p99가 39 ms라서 계산 여유가 충분하다고 보지는 않습니다. 또 같은 조건의 PP 측정이 아직 없어서, PP보다 낫다고 말씀드릴 수 있는 단계는 아닙니다.
>
> **[실차]** Jetson Orin의 ROS2 Jazzy에서 빌드를 마쳤습니다. 실차용으로는 별도 안전 게이트를 만들었습니다. 조이스틱을 누르고 있을 때만 동작하고, 수동 조작이 우선하며, E-stop은 걸리면 유지되고, 입력이 0.2초 끊기면 정지하고, 다른 제어기가 함께 돌면 거부합니다. 실차에서 DDS 통신 설정 문제로 MPC 노드가 센서를 찾지 못하던 것을 해결했고, 기존 스택과 함께 명령을 내보내지 않는 Shadow 모드로 몇 차례 실행했습니다. 오늘은 특정 맵에 묶이지 않도록 실행 중인 글로벌 경로를 받게 수정했습니다. **하지만 바퀴를 띄운 bench 시험과 실제 주행은 아직 하지 않았습니다.** 또 Shadow에서의 계산 성공 여부와 Jetson 계산 시간을 기록으로 남기지 못했고, 조향 부호, 휠베이스, E-stop 하드웨어 같은 차량 파라미터도 아직 실측하지 않았습니다.
>
> **[장애물 회피]** MPC 자체에는 장애물 제약이 없습니다. 시뮬레이션에서는 기존 회피 플래너가 만든 경로를 MPC가 따라가도록 연결만 되어 있고 검증은 하지 않았습니다. 상대차 추종 상태에서는 정지합니다. 실차에서는 회피 없이 글로벌 경로만 따라가고, 전방에 장애물이 가까우면 정지하도록 했습니다.
>
> **[향후 계획]** 먼저 Shadow 기록으로 Jetson 계산 시간을 측정하고, 차량 파라미터를 실측한 뒤 bench와 0.2 m/s 저속 주행으로 넘어가겠습니다. 시뮬레이션 튜닝은 계산 예산(horizon, dt), 추종 가중치(Q), 부드러움(R, Rd), 속도 상한 순서로 하나씩 바꿔 가겠습니다. 매번 랩타임, 추종 오차, 계산 시간, 제어 주기, 정지 횟수를 측정하고, 같은 조건에서 PP와도 비교하겠습니다. 그다음 회피 경로 추종 검증으로 넘어가겠습니다. 이상입니다.
