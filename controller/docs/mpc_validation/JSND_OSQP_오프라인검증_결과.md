# JSND OSQP 설치 및 오프라인 검증 결과

작성일: 2026-11-17

## 결론

남은 27개 MPC 테스트를 포함한 전체 **64개 테스트가 통과**했다. 하지만 실제 시간으로 20ms 간격을 두고 실행한 900회 중 전체 제어 계산이 **2회 20ms를 초과**했다. 따라서 노트북 오프라인 기능 검증은 통과했으나 **50Hz 주기를 항상 만족한다고 판정할 수 없다**.

## 설치 및 변경 범위

- 격리 가상환경: `/tmp/jsnd-mpc-validation-klk2k41_/venv`.
- OSQP 1.1.3, NumPy 1.26.4, SciPy 1.15.3, pytest 8.3.5, PyYAML 6.0.3을 이 가상환경에만 설치했다.
- Python 3.10.12 / Intel Core Ultra 7 155H. BLAS 스레드는 `OPENBLAS_NUM_THREADS=1`로 지정했다.
- system-site-packages를 공유하지 않는 venv이며, 테스트 시 외부 PYTHONPATH와 사용자 site-packages 유입을 차단했다.
- 초기 pip 실행에서 기존 셸의 ROS Python 경로에 있는 의존성 경고가 보였지만, 외부 PYTHONPATH 제거 후 `pip check`는 `No broken requirements found`였다. OSQP 모듈 경로는 위 venv 내부로 확인했다.
- 샌드박스 DNS 제한으로 첫 다운로드는 실패했고, 승인된 네트워크 접근으로 같은 venv에 설치했다.
- 기존 ROS2 Jazzy/Conda 환경, JSND 소스·설정·Docker 복사본, 지도·웨이포인트는 변경하지 않았다.
- 점검 대상 25개 파일의 SHA-256 변화 없음. Git 상태도 작업 전후 동일하다.
- pytest 캐시를 비활성화하고 Python bytecode 생성을 억제했다. 테스트 로그와 결과는 모두 `/tmp`에 저장했다.
- ROS2 launch, 노드 실행, 실제 차량 명령 발행, 빌드는 수행하지 않았다.

## 테스트

`64 passed in 2.62s` — 실패/skip 없음. 이전에 통과한 37개와 남아 있던 27개를 함께 실행했다.

포함 범위: 직선·급커브·S자·우회/복귀 경로 추종, 조향각/변화율 제한, 수치 Jacobian, 외부 속도 배열 보존, yaw wrap, 중복/짧은/비정상 경로, 정지 상태, solver 실패·비정상 해·timeout, 복구, PP 회귀, 기존 속도 계산 보존, FTG/watchdog 우선순위.

일부 단위 테스트의 deadline 시계는 결정론적 검증을 위해 mock이다. 아래 두 벤치마크는 실제 wall clock을 사용하며 실패나 초과를 숨기지 않았다.

## 1. 대기 없는 연속 호출 벤치마크

모듈 900회와 `Controller.main_loop` 900회를 각각 실행했다. 모든 최적화가 solved였고 20ms 초과는 없었다. 아래 MPC 시간에는 참조 생성, QP 구성/갱신, OSQP 및 예측 검사가 포함된다.

| 경로 | 횟수 | MPC P95 / 최대(ms) | 전체 main_loop P95 / 최대(ms) | 횡오차 RMS(m) |
|---|---:|---:|---:|---:|
| 직선 | 200 | 2.629 / 3.933 | 4.290 / 5.626 | 0.01988 |
| 급커브 | 100 | 1.932 / 2.397 | 3.624 / 3.691 | 0.02783 |
| S자 | 250 | 2.174 / 5.600 | 4.366 / 7.681 | 0.01763 |
| 정적 장애물 우회·복귀 | 350 | 2.191 / 4.673 | 4.244 / 5.449 | 0.01652 |

OSQP 내부 runtime 최댓값은 0.217ms였다. 이는 QP 전처리·후처리를 제외하므로 전체 MPC 시간과 혼동하면 안 된다.

## 2. 실제 50Hz 간격 호출

ROS 없이 monotonic clock과 sleep을 이용해 20ms 간격으로 900회 호출했다. 합성 bicycle 상태를 갱신하고 기존 속도 계산과 MPC를 포함하는 `Controller.main_loop`를 실행했다. MPC 성공 시 일정한 합성 측정 속도를 사용하며, 실제 종방향 액추에이터 모델은 포함하지 않았다.

| 경로 | 횟수 | 전체 계산 P95(ms) | 전체 계산 최대(ms) | MPC 최대(ms) | 전체 계산 20ms 초과 |
|---|---:|---:|---:|---:|---:|
| 직선 | 200 | 8.455 | 24.339 | 12.329 | 2 |
| 급커브 | 100 | 4.701 | 7.188 | 4.779 | 0 |
| S자 | 250 | 7.642 | 13.602 | 8.239 | 0 |
| 정적 장애물 우회·복귀 | 350 | 5.829 | 10.598 | 5.437 | 0 |

- 전체 계산: P50 3.360ms / P95 7.035ms / P99 10.602ms / 최대 24.339ms.
- 20ms 계산시간 초과: 2/900회 (0.222%).
- 예정된 시작 시각부터 완료까지의 최대 시간: 24.556ms, 20ms 초과 2회.
- 시작 지연: P99 3.264ms / 최대 4.644ms.
- 900회 모두 OSQP solved. MPC 계산은 모두 15ms deadline 이내였으며, solver 실패·MPC deadline 정지 요청은 없었다.
- **전체 main_loop 계산시간 초과는 현재 MPC 내부 deadline으로 검출되지 않았다.** MPC 내부 시간 제한과 전체 제어 주기 보장은 별개임을 확인했다.
- 이 기록만으로 전체 초과 원인을 스케줄러, 기존 전처리 또는 특정 함수로 단정할 수 없다. 단계별 profiling은 별도 과제다. 원래 설정이나 코드를 바꿔 재측정하여 초과를 지우지 않았다.

## 해석과 실차 적용 전 남은 사항

1. 기능 단위 테스트 및 OSQP 연결은 통과했다. 합성 우회 경로 추종은 검증했지만 실제 LiDAR/플래너 실행이나 차량 footprint 충돌 검증은 하지 않았다.
2. 현재 측정에서는 평상시 계산 여유가 있으나 간헐적 전체 제어 시간 초과가 있으므로 50Hz 안정성 검증을 완료했다고 볼 수 없다.
3. 실제 차량 CPU에서 명령을 발행하지 않는 replay/shadow 검증과 전체 callback 예산 측정이 필요하다. 전체 deadline 감시·초과 대응은 향후 개선 후보다.
4. ROS executor, DDS 통신, 실제 Frenet 변환, 시각화, mux, 액추에이터 응답은 이번 측정에 포함되지 않는다. 전체 main_loop라는 표현은 이 mock 오프라인 호출 범위를 의미한다.
5. 합성 파라미터 L=0.32m, 조향각 한계=0.53rad, 변화율=2rad/s는 시험값이다. 실제 차량의 휠베이스·기준점·물리 한계·조향 지연·안전 노드 활성화 여부를 확인해야 한다.
6. 이전 JSND 보고서의 OSQP 설치 대기 문구는 이번 결과로 갱신된 상태이지만, 사용자 지시에 따라 워크스페이스 내부 문서는 수정하지 않았다. 이 별도 보고서가 후속 검증 결과다.
