# 1초 MPC 최대 주행 성능 최적화 결과

## 결론

기준 커밋 `e7c83a8`의 안정화된 1초 MPC와 결과를 보존하고 별도 브랜치에서 실험했다. 저장 로그를
먼저 분석한 뒤 3랩 탐색을 수행하고, 유망 후보 두 개만 test0 장애물 조건에서 11랩 검증했다.

160개 로컬 waypoint 후보는 test0 평균 랩타임을 13.618 s에서 13.396 s로 **0.222 s(1.6%)**
줄였고 충돌·정지·물리 한계 위반 없이 11랩을 완료했다. 하지만 PP의 11.732 s보다 14.2% 느리며,
20 ms 제어주기 초과율이 0.411%에서 11.063%로 늘고 최소 차체 여유가 0.049 m에서 0.031 m로
감소했다. 짧은 11_18_6 맵에서는 상태 머신이 로컬 경로를 70점으로 제한하므로 이 개선도
일반화되지 않는다.

종단 속도 1.5 m/s 후보는 3랩에서 유망했지만 독립 11랩에서 평균 14.072 s로 악화됐다. 따라서
새 성능 후보를 실차 설정으로 선정하지 않았다. 기존
`mpc_profile_obstacle_1s.yaml`은 변경하지 않았고, 160점 후보는 한계가 명시된 시뮬레이션 전용
`mpc_profile_obstacle_1s_laptime_candidate.yaml`로만 저장했다. 실차 배포와 주행은 수행하지
않았다.

## 동일 s 위치 로그 분석

사용자가 제시한 PP 평균속도 3.595 m/s와 MPC 3.026 m/s의 기존 11랩 원시 trace를 0.5 m 간격의
동일한 트랙 좌표 `s`에 정렬했다. 평균 랩 차이 1.886 s 중 **1.840 s(97.6%)가 s=22–30 m**에
집중됐다.

| 구간 s (m) | MPC−PP 시간 (s/lap) | PP−MPC 평균속도 (m/s) | MPC 평균 실패 비율 |
|---|---:|---:|---:|
| 22–24 | 0.582 | 1.578 | 17.05% |
| 24–26 | 0.618 | 2.422 | 5.36% |
| 26–28 | 0.292 | 1.632 | 0.59% |
| 28–30 | 0.348 | 1.864 | 5.59% |

가장 큰 단일 0.5 m 손실은 s=23.25 m의 0.192 s이며 PP/MPC 속도는 3.543/1.734 m/s였다.
s=24.75 m에서는 0.178 s를 잃었고 PP/MPC는 4.265/1.797 m/s였다. 이 구간은 두 번째 장애물
접근·통과와 일치한다.

원인은 OSQP 시간 자체보다 로컬 경로 끝을 정지점으로 취급하는 제동 포락선과 회피 곡률의
결합이다. 기존 80점 경로는 약 8 m 앞에서 끝나고, MPC는 미지의 경로를 대비해 끝 속도를 0으로
역전파한다. 그 결과 장애물 진입 전에 감속하고 통과 후에도 다음 로컬 경로가 공급될 때까지
재가속이 늦다. s=25.25–27.25 m처럼 계산 실패가 0%인 bin만으로도 0.522 s를 잃으므로 fallback은
손실을 키우지만 주원인 전체를 설명하지 않는다. s=20–24 m의 높은 계산 실패는 추가 감속을
만든다.

## 제한 탐색 결과

회피 거리는 0.35 m에서 더 줄이지 않았고 PP와 MPC에 같은 4.5 m/s² plant 횡가속 한계와
friction ellipse를 적용했다. 목적함수 탐색은 `q_position=30`과 `r_accel=0.02` 두 경우만
확인했으며 각각 14.48 s와 13.76 s로 악화되어 기존 `q_position=20`, `q_speed=20`,
`r_accel=0.05`를 유지했다.

종단 속도는 물리 곡률 상한으로 다시 제한되며 기본값은 0이다. 1.5 m/s는 가까운 실험에서
조기 감속을 줄였지만, 긴 검증에서는 회피 재계획과 랩별 상태 변화 때문에 일관된 이득이 없었다.
안전 포락선과 비상정지는 제거하거나 완화하지 않았다.

## 최고속도 상한과 plant 병목

실제 plant 명령 상한은 VESC 환산 `23250/4614 = 5.039 m/s`였고 모든 비교에 동일하게 적용했다.
제어기 상한 5/6/7/8/10 m/s의 3랩 평균은 각각 12.39/13.02/13.99/13.10/13.47 s였다. 제어기
상한을 높여도 실제 최고속도는 5.029–5.034 m/s에 머물렀다. 가상으로 plant까지 10 m/s로
풀었을 때 최고속도는 5.449 m/s였지만 평균 랩은 13.46 s로 개선되지 않았다. 더 높은 상한이
제동 부담만 키웠으므로 물리 plant 상한과 비상정지를 유지했다.

## 교차 맵 및 환경 검증

3랩 스크리닝에서 test0 무장애물은 종단 1.5 m/s/160점 후보가 각각 11.03/11.38 s였다. 그러나
11_18_6 무장애물에서는 각각 5.32/5.15 s였고 동일 물리 한계의 PP 11랩은 4.816 s였다.

11_18_6은 총 141 waypoint라 운영 상태 머신의 절반 제한에 의해 160점 요청이 70점으로
축소된다. 이 조건의 장애물 실험에서 종단 1.5 m/s는 1랩만 완료하고 종단 정지했으며, 70점
기존 포락선은 3랩을 완료했지만 정지 4회, 실패율 22.62%, 평균 9.24 s였다. 같은 플래너와
물리 한계의 PP는 11랩 평균 6.076 s, 회피 100%, 충돌·정지·물리 위반 0이었다. 따라서 성능
후보는 11_18_6 장애물 환경에 일반화됐다고 판단할 수 없다.

11_18_6 장애물은 트랙 폭을 확인해 s=2.09 m, d=-0.10 m와 s=7.25 m, d=+0.10 m에 0.30 m
정사각 장애물을 배치했다. test0와 같은 운영 spliner와 0.35 m 회피 거리를 사용했지만, 합성
tracked-obstacle 메시지를 주입한 폐루프 실험이다. LiDAR 검출·clustering·tracker dropout과
전체 ROS executor timing은 검증 범위 밖이다.

## 선정 설정과 남은 문제

실차 검증을 위해 유지할 설정은 커밋 `e7c83a8`의 안정 프로파일이다. 1초 비균일 N=10,
`q_position/q_speed/r_accel=20/20/0.05`, 80개 로컬 waypoint, 종단 속도 0,
회피 거리 0.35 m다. 성능 후보는 같은 MPC 설정에서 test0 로컬 waypoint만 160개로 늘린다.

남은 문제는 다음과 같다.

- test0 성능 후보도 PP보다 1.664 s 느리고 50 Hz 전체 주기 기준을 만족하지 못한다.
- 11_18_6 장애물에서 MPC 정지와 높은 fallback 비율이 남아 범용 성능 프로파일이 아니다.
- test0 160점 후보의 0.031 m 최소 차체 여유는 실차 오차를 흡수할 근거가 없다.
- 최고속도보다 s=22–30 m의 회피 경로/로컬 경로 끝 제동과 재가속이 지배적이다.
- offline kinematic bicycle 결과는 실제 타이어 slip, 측정 지연, ROS scheduling을 대체하지 않는다.

이 조건 때문에 성능 후보를 실차 실행 명령이나 기본 프로파일에 연결하지 않았다. 추가 무한 반복
튜닝 없이 저장 결과, 실패 원인, 시뮬레이션 전용 파라미터를 남기고 종료한다.

## 코드 검증

변경 Python 파일은 모두 `py_compile`을 통과했고, production 패키지를 명시적으로 고정한 직접
검증에서 종단 속도 0/1.5 m/s의 포락선 끝값과 상한 초과 설정 거부를 확인했다. 저장 결과 분석
스크립트는 CSV와 세 그래프를 재생성했다.

저장소의 전체 pytest 묶음은 현재 환경의 두 기존 문제 때문에 green이 아니다. 상위 checkout의
구형 `controller`가 섞이는 `preview_grid_power` 1건(40건 통과 후 실패)과 이번에 수정하지 않은
planner의 `side_committed` debug-key 2건(25건 통과 후 실패)이다. 시뮬레이션 runner는 이 혼합을
막기 위해 현재 checkout의 production controller 패키지를 명시적으로 고정한다. 이 실패를 새
성능 코드가 통과했다고 기록하지 않는다.
